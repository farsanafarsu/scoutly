# Scoutly

Marketing site for Scoutly, an SEO, AEO and GEO intelligence platform. Static HTML with no build step at runtime, so it can be hosted on GitHub Pages as-is.

## Structure

| Path | What it is |
| --- | --- |
| `index.html` | Homepage (hand-edited; inline CSS and JS) |
| `login.html` | Account / audit setup preview (`noindex`) |
| `website-seo-audit/`, `backlink-checker/`, `broken-link-checker/`, `keyword-research/`, `competitor-analysis/`, `ai-search-visibility/`, `aeo-geo/` | Feature pages (generated) |
| `seo-glossary/`, `about/`, `404.html` | Resource, company and error pages (generated) |
| `sitemap.xml`, `robots.txt` | Generated |
| `assets/site.css`, `assets/site.js` | Shared styles and scripts for the generated pages. `site.js` also handles the homepage's mobile menu and URL scan forms |
| `tools/` | Page generator, site checker and domain config |

## Editing generated pages

Feature pages, the glossary, the about page, the 404 page, the sitemap and robots.txt are generated from `tools/build-pages.mjs`. Edit the content there, then run:

```sh
node tools/build-pages.mjs   # rebuild pages, sitemap.xml and robots.txt
node tools/check-site.mjs    # broken links/fragments, one h1 per page, unique titles, canonicals, JSON-LD
```

Commit the generated files. No dependencies are needed (Node 18+).

## Before deploying

1. Set the real domain in `tools/site.config.mjs` (it's currently the placeholder `https://scoutly.example`), then run `node tools/build-pages.mjs`. This also updates the canonical, Open Graph and JSON-LD URLs in `index.html`.
2. `404.html` uses root-relative links (`/…`), which assumes the site is served from the domain root (a custom domain). If you deploy to a project URL such as `user.github.io/scoutly/`, adjust those links.

## The app's tools (the `/api` server)

The app pages (dashboard, audits, keyword and domain tools) call `/api/…`, answered by the Python server in `seo/` (standard library only, Python 3.12+).

- **Locally:** `python server.py` (or `python server.py 9000` for another port) serves the whole site with the API at http://localhost:8000.
- **Live:** Cloudflare serves the pages. `worker.js` runs only for `/api/*` and forwards it to the same server hosted on Render (`render.yaml`). The Worker adds a shared key, and the hosted server (`SCOUTLY_API_ONLY=1`) refuses requests without it and serves nothing but the API.

### Connecting the live site

1. **Render:** New → Blueprint → pick this repository. It creates `scoutly-api` from `render.yaml`. When it's live, note its URL (`https://scoutly-api-….onrender.com`) and copy the generated `SCOUTLY_PROXY_KEY` from the service's Environment tab.
2. **Cloudflare:** Workers & Pages → `scoutly` → Settings → Variables and Secrets → add a **Secret** named `API_KEY` with that key.
3. Put the Render URL in `API_ORIGIN` in `wrangler.jsonc` (no trailing slash) and push to `main`. Set it there, not in the dashboard: a deploy replaces dashboard variables with the ones in `wrangler.jsonc`.
4. Check: `https://<your site>/api/health` should return `{"ok": true}`, then try Domain Overview.

Render's free plan sleeps after 15 minutes without traffic, so the first tool run after a quiet spell can take up to a minute. Optional Render variables: `PAGESPEED_API_KEY` (own PageSpeed quota), and `DATAFORSEO_LOGIN` / `DATAFORSEO_PASSWORD`, which turn on paid data billed to that account for anyone using the live site.

### The team's backlinks database

The Backlink Manager saves every backlink, edit, deletion and status check to MongoDB automatically, so the whole team shares one list. SEO Campaigns are saved the same way, in a `campaigns` collection next to `backlinks`. Until it's set up, each browser keeps its own links and campaigns (they survive logging out), and they move into the database the first time that browser connects.

1. **MongoDB Atlas** (free): create a cluster, add a database user, allow access from anywhere (`0.0.0.0/0`, since Render's free plan has no fixed IP), then copy the connection string (`mongodb+srv://USER:PASSWORD@….mongodb.net/`).
2. **Render** → `scoutly-api` → Environment: set `MONGODB_URI` to that string. `SCOUTLY_TEAM_KEY` is generated by `render.yaml`; if it isn't there, add a long random value. Save, and Render redeploys (it now runs `pip install -r requirements.txt` to get pymongo).
3. **Share the team key** with your teammates privately. Each person pastes it once on the Backlink Manager; it's kept in their browser.

Without a team key, a hosted server keeps the shared list switched off, so nobody who simply finds the site can read it. Optional: `MONGODB_NAME` (default `scoutly`).

### SEO Action Center

`action-center.html` turns real findings into tasks. The server side is `seo/taskstore.py` (storage), `seo/actions.py` (issue rules and priorities) and `seo/taskjobs.py` (background scans). The routes are under `/api/tasks/*` in `seo/engine.py`.

- **Storage:** tasks are kept only in the team database (`MONGODB_URI`), in the `tasks` and `task_scans` collections. Indexes are created on first use, so there are no migrations. A unique `(project, fp)` index stops repeat scans from creating duplicate tasks.
- **Access:** the same `SCOUTLY_TEAM_KEY` as the backlinks. There are no per-user accounts, so everyone with the key sees every website's tasks, and the "by" name comes from the browser.
- **Sources:**
  - Site Audit and PageSpeed Insights (`PAGESPEED_API_KEY` is optional).
  - Backlink Manager links.
  - Search Console exports imported in Position Tracking. There's no live Google Search Console connection yet.
- **Settings:** thresholds can be overridden with `SCOUTLY_TASK_RULES`, a JSON object (see `RULES` in `seo/actions.py`).
- **Not available:** email notifications, because there's no email service.
- **Try it locally:** set `SCOUTLY_DEV_MEMORY_DB=1` to keep tasks in memory (lost when the server stops), or use the `scoutly-memory-db` launch config.
- **Tests:** `python -m unittest discover tests`

### Blog Bank

`blog-bank.html` drafts up to 10 SEO blogs at a time with AI, saves them, and lets you edit and copy them into a website later. The server side is `seo/blogbank.py` (storage, background generation, HTML clean-up) and `seo/blogai.py` (the Anthropic API calls). The routes are under `/api/blogs/*` in `seo/engine.py`.

- **Storage:** drafts are kept only in the team database (`MONGODB_URI`), in the `blogs` and `blog_versions` collections, so they're the same on every device and survive logging out. Earlier versions are kept on every Save, every 10 minutes while autosaving, and before AI rewrites or restores (the last 25 per blog).
- **Access:** the same `SCOUTLY_TEAM_KEY` as the backlinks and Action Center. Drafts belong to the team workspace; there are no per-user accounts yet, so everyone with the key sees every draft, and the "created by" name comes from the browser.
- **AI writing:** set `ANTHROPIC_API_KEY` on Render. It stays on the server. Optional: `SCOUTLY_AI_MODEL` (default `claude-opus-5-5`) and `SCOUTLY_AI_EFFORT` (default `medium`). Each blog is one streamed request that returns JSON matching a schema; refusals are retried server-side on Anthropic's recommended fallback model.
- **Limits:** 10 blogs per batch, 3 written at a time, at most 40 blogs and 60 section rewrites an hour per server (a guard against runaway costs). Each blog is saved as a draft before it's written, so a failure only affects that blog, and it can be retried on its own. If the server restarts mid-batch, unfinished blogs show as failed after 25 minutes and can be retried.
- **Internal links:** when a website is given, the generator reads its sitemap (the Indexability checker's code) and only suggests real URLs from it.
- **Try it locally:** `SCOUTLY_DEV_MEMORY_DB=1` keeps drafts in memory. Without `ANTHROPIC_API_KEY` generation is off, but everything else works.
- **Tests:** `python -m unittest tests.test_blog_bank` (no database or AI calls needed).
